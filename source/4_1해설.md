# 4-1 해설

### 1. ②
[A-1. 거대 언어 모델의 학습 패러다임]
Pre-training은 방대한 텍스트로 언어와 지식을 배우는 단계이고, Post-training은 사람이 원하는 방식으로 대화하고 안전하며 유용하게 동작하도록 만드는 단계다. ①은 두 단계를 뒤바꾼 설명이고, ③은 사용 데이터를 반대로 서술했다. ④의 외부 저장소 조회는 B챕터의 RAG 개념이다.

### 2. ③
[A-2. Pre-training]
Pre-training의 대표 학습 목표는 앞선 토큰들을 보고 다음 토큰을 예측하는 Next Token Prediction이다. ①은 RLHF의 선호 비교, ②는 RLVR의 검증 가능한 보상, ④는 B챕터 Bi-encoder의 대조 학습에 해당한다.

### 3. ①
[A-2. Pre-training 후 모델의 한계]
Pre-training만 거친 모델은 사용자의 의도를 수행하도록 학습된 것이 아니라 다음 토큰을 잘 예측하도록 학습되었다. 그래서 질문에 답하는 대신 비슷한 형식의 질문을 이어서 생성한다. 지식의 양이나 검색, 보상 모델과는 관계가 없다.

### 4. ④
[A-1. Post-training 대표 기법]
문서가 제시한 Post-training 대표 기법은 Instruction-tuning, RLHF, DPO, RLVR 네 가지다. Contrastive Learning은 B챕터에서 Bi-encoder retriever를 학습할 때 쓰는 방식으로 Post-training 기법이 아니다.

### 5. ②
[A-4. Fine-tuning]
Fine-tuning은 이미 사전 학습된 기존 모델을 특정 작업이나 도메인에 맞게 추가로 학습시키는 과정이다. ①은 Pre-training, ③은 RLHF의 Reward Model 학습, ④는 RAG의 검색 과정에 해당한다.

### 6. ①
[A-4. Instruction-tuning이란?]
Instruction-tuning은 언어모델이 사람이 내린 지시문을 따르도록 학습하는 단계이며 Fine-tuning의 한 종류다. ②는 RLHF의 강화학습 단계, ④는 B챕터 LangChain 기반 RAG의 인덱싱 과정이다.

### 7. ③
[A-4. 일반 Fine-tuning과의 차이]
일반 Fine-tuning은 특정 Task에 맞춰 모델을 조정하는 반면, Instruction-tuning은 다양한 Task의 지시문을 이해하고 수행하도록 학습하며 새로운 형태의 지시에도 일반화하는 것을 목표로 한다.

### 8. ②
[A-4. Instruction-tuning의 핵심 구조]
핵심 구조는 Instruction, Input, Output이다. ①은 B챕터 IR의 구성 개념, ③은 C챕터 강화학습 Agent의 요소, ④는 C챕터 MCP 아키텍처의 구성요소다.

### 9. ④
[A-5. 많은 Task를 가진 데이터로 학습]
Super-NaturalInstructions는 약 1.6K개 이상의 task와 3M개 이상의 예시로 구성된다. ①의 52K는 Alpaca, ②의 16,000+는 C챕터 ToolLLM, ③의 6,000개는 C챕터 WebGPT의 규모다.

### 10. ①
[A-5. 학습 후 평가]
Instruction-tuning의 목표는 지시 일반화이므로, 학습하지 않은 새로운 task에서 평가해 instruction generalization 능력을 확인한다. ③은 RLHF의 선호 비교, ④는 RLVR의 검증 방식이다.

### 11. ③
[A-6. MMLU]
MMLU는 57개의 지식을 요구하는 태스크에서 언어모델의 광범위한 지식과 문제 해결 성능을 평가하는 벤치마크다. ①은 ToolLLM 계열, ②는 D챕터의 웹 에이전트 환경에 대한 설명이다.

### 12. ②
[A-6. K-MMLU]
K-MMLU는 한국의 지식 환경에 맞게 구성되어 문화, 지역, 법률 등 한국 특화 지식을 요구한다. 단순 번역본이 아니라는 점이 핵심이다. ③은 RLVR이 적용되는 문제 유형, ④는 RLHF의 선호 데이터에 해당한다.

### 13. ①
[A-8. Alpaca와 Instruction-following 데이터]
Alpaca는 LLaMA 7B를 기반으로 약 52K개의 instruction-following 데이터로 Fine-tuning한 모델이다. ②의 6,000개는 WebGPT, ③의 16,000+ API는 ToolLLM, ④는 Super-NaturalInstructions에 해당한다.

### 14. ④
[A-8. Alpaca 데이터 생성 흐름]
Alpaca는 강력한 모델과 기존 seed tasks를 활용해 Modified Self-Instruct Generation 방식으로 약 52K개의 예시를 생성했다. ②는 C챕터 Toolformer의 데이터 생성 방식, ③은 B챕터 Cross-encoder의 계산 방식이다.

### 15. ③
[A-9. Instruction-tuning의 한계]
문서가 제시한 한계는 정답이 없는 task의 존재, 모든 오류를 동일하게 취급하는 문제, 사람이 만든 답변이 최적이 아닐 수 있다는 점이다. 외부 저장소 갱신 문제는 B챕터에서 RAG의 필요성으로 제시된 내용이다.

### 16. ②
[A-9. 문제 2. 모든 오류를 동일하게 취급]
지도학습 방식은 아주 사소한 오류와 치명적인 오류를 동일한 loss로 처리할 수 있다. 실제 사람의 관점에서는 오류의 심각도가 다르다는 것이 지적의 핵심이다.

### 17. ①
[A-10. 언어모델의 목적함수와 인간 선호]
사람이 선호하는 답변은 정확성, 유용성, 관련성, 안전성 등을 포함하는데 다음 토큰 확률을 높이는 목적함수만으로는 이를 정의하기 어렵다. 그래서 LM Objective와 Human Preference 사이에 차이가 생긴다.

### 18. ④
[A-12. Human-in-the-loop ML]
흐름은 사람이 레이블링하고 모델을 학습한 뒤, 헷갈리는 데이터를 골라 다시 사람이 평가하고 이를 반복하는 것이다. ①은 RAG 파이프라인, ②는 Toolformer 데이터 생성, ③은 ReAct 루프에 해당한다.

### 19. ②
[A-13. 인간 선호를 반영한 최적화]
사람이 느끼는 선호도를 보상으로 표현할 수 있다고 가정하면, 모델의 목표는 응답에 대한 기대 보상을 최대화하는 것이 된다.

### 20. ③
[A-14. RLHF]
RLHF는 인간의 피드백을 통해 언어모델이 사람이 선호하는 답변을 생성하도록 학습하는 방식이다. ①은 RLVR, ②는 DPO, ④는 Instruction-tuning에 대한 설명이다.

### 21. ①
[A-15. RLHF 파이프라인]
순서는 1단계 Instruction-tuning 또는 SFT, 2단계 비교 데이터 수집, 3단계 Reward Model 학습, 4단계 PPO 등 강화학습으로 정책 최적화다. 보상 모델이 있어야 강화학습이 가능하므로 순서가 뒤바뀔 수 없다.

### 22. ④
[A-16. 절대 점수 대신 상대 비교]
인간의 절대 점수 평가는 일관성이 낮고 사람마다 기준이 다르며 같은 사람도 상황에 따라 달라진다. 그래서 응답 두 개를 비교해 더 나은 답을 고르는 방식을 사용한다. 강화학습 제거는 DPO의 특징이므로 혼동하면 안 된다.

### 23. ②
[A-17. Reward Model과 Pairwise Comparison]
사람이 더 선호한 응답의 보상이 그렇지 않은 응답의 보상보다 크도록 학습한다. ①의 절대 점수 회귀는 일관성 문제로 채택되지 않았고, ③은 Cross-encoder, ④는 RLVR의 검증 가능한 보상이다.

### 24. ①
[A-20. Reward Model 주의점]
데이터와 모델 크기가 커지면 validation accuracy는 오르지만 단일 인간 평가 수준에 근접한다고 해서 완벽한 것은 아니다. Reward Model이 잘못되면 이후 강화학습도 잘못된 방향으로 진행된다.

### 25. ③
[A-22. Reward Hacking]
Reward Hacking은 모델이 실제 목표를 달성하는 대신 보상 함수를 공략해 높은 점수를 얻는 방향으로 행동하는 현상이다. ①은 Over-optimization과 반대되는 상황, ②는 B챕터의 검색 노이즈, ④는 B챕터의 Conflict다.

### 26. ②
[A-22. Chatbot 보상 구조의 부작용]
답변을 잘해준다는 보상이 더 길게, 자신감 있게, 그럴듯하게 말하기로 연결될 수 있다. 그 결과 실제 사실 여부와 관계없이 답변을 생성하는 Hallucination이 발생할 수 있다.

### 27. ④
[A-22. Reward Model Over-optimization]
Reward Model의 예측 점수는 계속 증가하지만 실제 사람의 preference는 오히려 감소할 수 있다. 보상 모델이 실제 선호의 완전한 대리 지표가 아니기 때문이다.

### 28. ①
[A-23. DPO]
DPO의 핵심 아이디어는 RLHF에서 강화학습 단계를 제거하는 것이다. 별도의 보상 모델을 명시적으로 학습하지 않고 선택된 답과 거절된 답을 이용해 언어모델을 직접 최적화한다. ③은 Toolformer의 자기지도, ④는 RLVR의 방식이다.

### 29. ③
[A-24. RLVR]
RLVR은 수학이나 코딩처럼 정답 검증이 가능한 문제에서 Verifier로 보상을 계산하는 방식이며 DeepSeek-R1이 대표적인 성공 사례다. 정답이 없는 개방형 창작 문제와는 오히려 맞지 않는다.

### 30. ②
[B-1. Retrieval-Augmented LM 기본 개념]
Retrieval-Augmented LM은 추론 시 외부 데이터 저장소를 불러와 활용하는 언어모델이다. 학습 단계에 지식을 통합하는 것이 아니라 test time에 Datastore를 조회한다는 점이 핵심이다.

### 31. ①
[B-1. Parametric / Non-parametric Knowledge]
Parametric Knowledge는 모델 파라미터 내부에 저장된 지식이고 Non-parametric Knowledge는 외부 저장소의 지식이다. RAG는 이 둘을 함께 활용한다.

### 32. ④
[B-3. Datastore]
Datastore는 가공되지 않은 대규모 텍스트 코퍼스일 수 있으며, 반드시 라벨링된 데이터셋일 필요도 Knowledge Base처럼 완전히 구조화된 데이터일 필요도 없다. 따라서 ④가 옳지 않다.

### 33. ③
[B-4. Query]
언어모델의 최종 입력과 Query가 반드시 동일한 것은 아니다. 사용자의 질문을 그대로 검색할 수도 있고, 검색에 적합한 형태로 변환한 query를 사용할 수도 있다.

### 34. ①
[B-5. Index]
Index는 문서나 단락과 같은 검색 가능한 항목을 체계적으로 정리하여 더 쉽게 찾을 수 있도록 하는 구조다. Inverted Index나 Vector Index가 대표적이다.

### 35. ④
[B-8. Information Retrieval]
IR은 외부 데이터 저장소에서 사용자의 질의에 맞는 정보를 검색하는 과정이다. 언어모델이 내부 파라미터만 사용하여 정보를 생성하는 것은 기존 Language Model 방식이므로 ④가 옳지 않다.

### 36. ②
[B-9. IR 활용]
문서가 제시한 활용 분야는 웹 서치와 아이템 서치, 추천 시스템, 그리고 검색증강생성이다. ①의 지식 편집은 오히려 RAG의 대안으로 언급된 개념이다.

### 37. ③
[B-10. Retriever]
Retriever는 사용자의 Query에 맞는 후보 문서를 저장소에서 찾아오는 모듈이며 RAG에서 첫 번째 핵심 단계 역할을 한다. ①은 Generator, ④는 C챕터 MCP의 역할이다.

### 38. ①
[B-11. Retriever의 종류]
Sparse Retriever는 어휘적 유사도에, Dense Retriever는 의미적 유사도에 기반한다. Bi-encoder와 Cross-encoder는 Dense Retriever 내부의 구조 구분이므로 혼동하면 안 된다.

### 39. ④
[B-11. Retriever의 대표 기법]
Sparse는 TF-IDF와 BM25, Dense는 DPR과 Contriever, OpenAI Embeddings가 대표적이다. ③의 Cross-encoder와 Bi-encoder는 둘 다 Dense Retriever의 구조이므로 Sparse와 Dense를 나누는 기준이 아니다.

### 40. ②
[B-12. TF-IDF]
TF는 특정 단어가 문서에서 얼마나 자주 등장하는지를, IDF는 그 단어가 전체 코퍼스에서 얼마나 드물게 등장하는지를 나타낸다.

### 41. ③
[B-12. IDF의 의미]
this, is, and 같은 단어는 거의 모든 문서에 등장하므로 IDF 값이 낮아지고 결과적으로 TF-IDF 가중치가 0에 가까워진다. TF가 낮아서가 아니라 IDF가 낮아지는 것이 이유다.

### 42. ①
[B-12. TF-IDF 수식]
가중치는 문서 내 단어 빈도에, 전체 문서 수를 해당 단어가 등장한 문서 수로 나눈 값의 로그를 곱해 계산한다. 즉 문서 내 빈도와 전체 코퍼스에서의 희귀도를 함께 반영한다.

### 43. ④
[B-13. Sparse Retriever의 장점]
장점은 구현과 이해가 쉬운 단순성, Inverted Index 구조를 통한 효율성, 어떤 단어가 매칭되었는지 설명 가능한 투명성이다. ①과 ②는 Dense, ③은 Cross-encoder의 특징이다.

### 44. ②
[B-13. Sparse Retriever의 단점]
Sparse 방식은 의미 이해가 제한되어, bad guy와 villain처럼 의미는 유사하지만 단어가 다르면 매칭에 실패할 수 있다. ①과 ④는 Dense Retriever의 단점이다.

### 45. ③
[B-15. Bi-encoder]
Bi-encoder는 Query와 Document를 독립적으로 각각 인코딩한 뒤 임베딩 간 유사도로 관련성을 계산한다. ①과 ②는 Cross-encoder, ④는 Sparse 방식의 설명이다.

### 46. ①
[B-16. Cross-encoder]
Cross-encoder는 두 텍스트를 하나의 시퀀스로 결합해 Transformer에 입력하며, Self-Attention을 통해 모든 Query 토큰과 Document 토큰이 직접 상호작용한다. ②와 ③은 Bi-encoder의 특징이다.

### 47. ④
[B-17. Bi-encoder vs Cross-encoder]
Cross-encoder는 모든 질의와 문서 쌍을 개별로 계산해야 하므로 계산 비용이 크고 느리다. 따라서 전체 문서 집합 검색보다는 Reranking 단계에 적합하며 ④는 옳지 않다.

### 48. ②
[B-18. Dense Retriever의 장점]
Dense Retriever는 동의어와 다양한 표현을 의미 수준에서 처리하고, 복잡하고 긴 질의도 벡터 공간에서 풍부하게 표현할 수 있다. ①과 ④는 Sparse의 장점이다.

### 49. ③
[B-18. Dense Retriever의 단점]
단점은 높은 연산 비용, 블랙박스처럼 동작해 낮은 투명성, 그리고 학습 데이터와 임베딩 모델 품질에 크게 좌우되는 데이터 및 모델 의존성이다. ①은 Sparse의 단점이다.

### 50. ①
[B-20. 이유 1. 모든 지식을 파라미터에 저장하지 못함]
LLM은 사전학습 데이터에 자주 나타나는 정보를 더 잘 기억하는 경향이 있어 희귀하거나 최신인 정보는 누락할 수 있다. RAG는 자주 등장하지 않는 정보에 대한 지식 공백을 보완한다.

### 51. ④
[B-20. 이유 2. 지식이 금방 뒤처지고 갱신이 어려움]
현재의 지식 편집 방식은 확장성이 부족한 반면, Datastore는 쉽게 추가하고 수정하여 최신 상태를 유지할 수 있다. 그래서 최신 정보가 필요한 상황에 RAG가 유리하다.

### 52. ②
[B-20. 이유 3, 4. 검증 가능성과 보안 정보]
RAG는 참고 문서와 출처를 제시해 답변의 검증을 가능하게 하고, 기업 내부 문서처럼 학습에 넣기 어려운 정보도 검색으로 활용할 수 있게 한다. 다만 검색을 쓴다고 정확성이 항상 보장되지는 않는다.

### 53. ③
[B-21. RAG 파이프라인]
파이프라인은 질문 추출과 해석, 문서 검색, 그리고 검색 결과 기반 답변 생성의 순서다. 검색이 생성보다 먼저 이루어져야 근거 기반 답변이 가능하다.

### 54. ①
[B-23. Challenge 1. Context 구성]
필요한 정보를 어떻게 Context에 구성할지가 문제이며, 해결 방향으로 언어모델의 Context Length 확장이 제시된다. 검색 결과를 많이 넣는다고 항상 좋아지는 것은 아니다.

### 55. ④
[B-24. Challenge 2. 검색 모델 성능 의존]
RAG의 결과는 검색 모델 성능에 의존하며 컨텍스트 내 잘못된 정보를 모델이 무시하기 어렵다. 따라서 정보검색을 사용한다는 사실만으로 사실 정확성이 보장되지는 않는다.

### 56. ②
[B-25. Training with Noises]
Noise Robustness는 외부 문서에 관련 없는 정보가 섞여 있어도 올바른 답을 찾아내는 능력이고, Negative Rejection은 검색 문서에 정답 정보가 없을 때 추측하지 않고 답변을 거부하는 능력이다.

### 57. ③
[B-26~B-28. Conflict와 해결]
사전지식과 컨텍스트가 충돌할 때의 해결책은 두 가지다. 주어진 컨텍스트에만 근거해 답하도록 Grounding 학습을 강화하는 것과, 컨텍스트에 정보가 없을 때 답변을 회피하거나 거절하도록 학습하는 것이다.

### 58. ①
[B-29. Challenge 4. 복잡한 추론과 사실 오류]
Information Integration은 여러 문서의 내용을 종합해 정답을 만드는 능력이고, Counterfactual Robustness는 사실과 반대되는 정보가 Context에 주어져도 이를 적절히 처리하고 지적하는 능력이다.

### 59. ②
[C-1. Agent란?]
Russell과 Norvig의 정의에 따르면 Agent는 센서를 통해 환경을 인지하고 액추에이터를 통해 환경에 액션으로 영향을 미치는 것으로 간주될 수 있는 모든 것이다.

### 60. ③
[C-2. 강화학습과 Agent]
강화학습에서 Agent와 환경의 상호작용은 Observation, Action, Reward로 구성된다. ①은 A챕터 Instruction-tuning 구조, ④는 MCP 아키텍처의 구성요소다.

### 61. ①
[C-3. LLM Agent]
LLM Agent는 거대언어모델을 핵심 구조인 backbone으로 삼아 환경을 이해하고 행동을 수행하는 에이전트다. ③은 B챕터 RAG, ④는 MCP에 대한 설명이다.

### 62. ④
[C-3. LLM-first View와 Agent-first View]
LLM-first View는 기존 LLM을 활용한 시스템을 에이전트로 만드는 관점으로 서치, 심리상담, 코드 에이전트가 예시다. Agent-first View는 LLM을 AI 에이전트에 통합해 언어를 활용한 추론과 의사소통을 가능하게 하는 관점으로 로봇과 임바디드 에이전트가 예시다. ①은 두 관점의 예시를 뒤바꾼 설명이다.

### 63. ②
[C-4. 이것은 Agent인가?]
웹을 탐색하는 시스템과 OS 파일을 검색해 코드로 처리하는 시스템은 Yes이지만, 검색하고 생성만 하는 시스템은 Probably not, 복잡한 추론만 하는 LLM은 툴도 없고 외부 환경과 상호작용하지 않으므로 No다. 핵심은 환경과의 상호작용과 Action 수행 여부다.

### 64. ③
[C-5. 성공적인 Agent가 갖추어야 할 요건]
문서가 제시한 요건은 Tool Use, Reasoning and Planning, Environment Representation, Environment Understanding, Interaction과 Communication이다. Reward Modeling은 A챕터 RLHF의 구성요소이지 Agent 요건이 아니다.

### 65. ①
[C-6. LLM Agent Framework - Controller]
Controller는 사용자 요청을 충족하기 위한 실행 가능한 계획을 제공하는 LLM의 핵심 두뇌 역할을 한다. ②는 Tool Set, ③은 Environment의 역할이다.

### 66. ④
[C-6. LLM Agent Framework - Perceiver]
Perceiver는 Environment의 feedback을 요약해 Controller에게 전달하는 역할을 한다. ①은 Controller, ③은 Environment의 역할이며 ②는 어느 구성요소에도 해당하지 않는 서술이다.

### 67. ②
[C-6. Tool Set과 Environment]
Tool Set은 서로 다른 기능을 가진 도구들의 집합이고, Environment는 도구들이 실제로 작동하는 플랫폼을 제공한다. ①은 두 역할을 뒤바꾼 설명이다.

### 68. ③
[C-6. Framework 흐름]
흐름은 Controller가 Planning을 수행해 Tool Set으로 이어지고, Tool Execution을 거쳐 Environment에서 실행된 뒤 Environment Feedback을 Perceiver가 요약해 다시 Controller로 전달하는 순환 구조다.

### 69. ①
[C-7. Tool이란?]
Tool은 언어 모델 외부에서 실행되는 프로그램에 연결되는 함수 인터페이스를 의미하며, LLM은 함수 호출과 입력 인자를 생성함으로써 이 도구를 활용한다.

### 70. ④
[C-7. Tool의 종류]
문서는 Physical Interaction-based Tools, GUI-based Tools, Program-based Tools 세 가지로 분류한다. 물리 세계에서 가상 세계로, 시각적 조작에서 프로그래밍 조작으로 이어지는 축으로 설명된다.

### 71. ②
[C-8. Tool Use Paradigm]
Tool Use는 텍스트 생성 모드와 도구 실행 모드 두 모드 간의 전환으로 볼 수 있다. ④는 MCP의 계층 구분이므로 혼동하면 안 된다.

### 72. ③
[C-8. Tool Use 예시]
사용자가 날씨를 물으면 언어모델이 툴 호출 토큰을 생성하고, 이 호출이 외부 서버에서 실행되어 결과가 반환되며, 모델은 그 결과로 API 호출 토큰을 대체해 최종 답변을 만든다.

### 73. ①
[C-9. Tool 사용을 유도하는 방법]
문서는 추론 시 프롬프트로 유도하는 Inference-time Prompting과, 학습을 통해 언제 툴을 써야 하는지 익히게 하는 Tool Learning 두 가지를 제시한다.

### 74. ④
[C-10. Tool Learning - Imitation Learning]
모방 학습은 인간의 도구 사용 행동 데이터를 기록함으로써 언어모델이 인간의 행동을 모방하도록 학습하는 방식으로, 가장 간단하고 직관적인 방식이다. ①은 Toolformer의 자기지도 방식이다.

### 75. ②
[C-11. WebGPT]
WebGPT는 검색 엔진을 사용하기 위해 인간의 행동을 모방했으며, 지도 학습과 강화학습을 함께 사용했고 단 6,000개의 데이터만 필요했다. 장문 질의응답에서 뛰어난 성능을 보였다.

### 76. ③
[C-12. Toolformer]
Toolformer는 모델 스스로 학습 데이터를 생성하는 자기지도 방식이며, 검색 엔진뿐 아니라 질의응답, 위키 검색, 계산기, 달력, 기계 번역 등 여러 API를 활용한다.

### 77. ①
[C-13. Toolformer 데이터 생성 과정]
순서는 API 호출 샘플링, API 실행, API 호출 필터링이다. 실행 결과가 있어야 그 호출이 문맥 예측에 유용한지 평가할 수 있으므로 필터링이 실행보다 앞설 수 없다.

### 78. ④
[C-14. ToolLLM]
ToolLLM은 기존 연구의 한계인 툴의 다양성과 범용성을 타겟팅한 연구로, 16,000개 이상의 실제 API를 활용해 대규모 학습 데이터셋과 특화 언어모델, 평가 벤치마크를 함께 제안했다.

### 79. ②
[C-16. Multi-modal Tool Learning]
멀티모달 대규모 언어모델을 기반으로 도구를 정의하고 활용하는 연구로 GUI 에이전트와 Embodied 에이전트가 예시다. 최근에는 화면을 직접 보고 마우스와 키보드를 조작하는 Computer Use Agent로 발전하고 있다.

### 80. ③
[C-17. MCP가 등장한 이유]
외부 툴 활용 연구가 급증하면서 회사와 모델마다 서로 다른 툴 호출 방식과 스키마를 만들었고, 그 결과 호환성이 부족하고 같은 툴도 모델이 바뀌면 다시 정의해야 하는 재사용 문제가 생겼다.

### 81. ①
[C-18. MCP]
MCP는 언어 모델이 외부 툴과 상호작용하기 위한 표준화된 방식으로 정의한 프로토콜이며, 툴 호출과 응답 전달, 컨텍스트 공유를 하나의 공통 규격으로 처리한다.

### 82. ④
[C-19. MCP Architecture]
MCP Host는 하나 또는 여러 MCP 클라이언트를 조정하고 관리하는 AI 애플리케이션, MCP Client는 서버와의 연결을 유지하며 컨텍스트를 가져오는 구성요소, MCP Server는 클라이언트에게 컨텍스트를 제공하는 프로그램이다. 각 Client는 Server와 일대일 연결을 형성한다.

### 83. ②
[C-20. MCP Layer]
Data Layer는 클라이언트와 서버 통신을 위한 JSON-RPC 기반 프로토콜을 정의하고, Transport Layer는 데이터 교환을 가능하게 하는 통신 메커니즘과 채널을 정의한다. 개념적으로 Data Layer가 내부 계층, Transport Layer가 외부 계층이다.

### 84. ③
[C-22. MCP의 장점]
문서가 제시한 장점은 표준화, 확장성, 호환성, 재사용성, 투명성 다섯 가지다. 은닉성이나 폐쇄성은 오히려 MCP가 해결하려는 문제와 반대되는 성질이다.

### 85. ①
[C-21, C-23. JSON-RPC 통합과 FastMCP]
MCP는 OpenAI Function Calling이나 Anthropic Tool Use처럼 제각각이던 툴 호출 구조를 JSON-RPC 형식의 공통 구조로 표현한다. 서버는 FastMCP 라이브러리로 간단히 구현할 수 있으며 stdio, HTTP, WebSocket 등 여러 전송 방식과 연결할 수 있다.

### 86. ③
[D-3. Agent가 환경을 이해하기 위해 필요한 것]
문서는 환경에 접근하기 위한 Tool, 환경의 Representation, 환경을 이해하고 탐사하기 위한 방법론 세 가지를 제시한다.

### 87. ①
[D-4. 환경 표현 - Text / ALFWorld]
ALFWorld는 텍스트 기반 임바디드 에이전트 시뮬레이션 엔진으로, 물리적 세계에 대한 정보를 언어모델이 텍스트 기반으로 이해하고 텍스트 명령을 통해 행동한다. ②는 Touchdown, ③은 WebArena에 대한 설명이다.

### 88. ④
[D-5. 환경 표현 - Image / Touchdown]
Touchdown은 Google Street View 기반의 Navigation 및 Instruction Following 데이터셋으로, 자연어 지시문에 따라 실제 도시 환경 이미지에서 경로를 탐색하고 목표 지점으로 이동한다.

### 89. ②
[D-7. Textual Web Representation / WebArena]
WebArena는 웹 환경을 HTML, DOM, Accessibility Tree 같은 구조화된 텍스트로 표현한다. 단순 스크린샷 이미지보다 구조화된 표현을 제공해 버튼 클릭이나 항목 선택을 정확히 수행하도록 돕는다.

### 90. ③
[D-6. 이미지 기반 표현의 문제점]
Agent가 좋은 성능을 내려면 세부적인 이해가 중요한데, OCR과 복잡한 레이아웃에서의 Grounding, UI 요소 위치 파악 등에서 많은 모델이 실패할 수 있다. 다만 높은 수준의 학습을 통해 개선이 가능하다.

### 91. ①
[D-8. 복잡한 환경에 대한 이해]
모델은 코딩 지식이나 일반적인 웹사이트 탐색 방법처럼 파라미터에 포함된 지식은 이미 알고 있지만, 현재 환경의 상태와 새 UI, 특정 툴, 시간적 변화 등은 실시간 환경 상호작용을 통해 발견해야 한다.

### 92. ④
[D-9. Environment-specific Prompt]
환경에 맞는 특정 프롬프트를 제공하면 환경 특성에 맞는 행동을 유도할 수 있다는 장점이 있지만, 새로운 환경으로 바뀌면 성능이 떨어지는 일반화 문제가 있다.

### 93. ②
[D-10. Agent Workflow Memory]
Agent Workflow Memory는 성공적으로 수행된 Workflow를 기억하고 이를 기반으로 새로운 Prompt를 자동 생성해 에이전트에게 제공한다. 사람이 매번 프롬프트를 설계하지 않고 경험을 통해 자동 생성하고 일반화하는 것이 핵심이다. ③은 Curiosity-based Reward, ④는 BAGEL이다.

### 94. ③
[D-11. Environment Exploration / Curiosity-based Reward]
예측하기 어려운 새로운 State Space에 들어갈수록 더 높은 reward를 제공해 새로운 상태 탐색을 유도하는 방식이다. 강화학습의 Exploration 문제와 연결된다.

### 95. ①
[D-12. Exploration-based Trajectory Memorization / BAGEL]
BAGEL은 명령을 샘플링해 실행하고 더 정확한 새로운 명령으로 Trajectory를 재라벨링한다. LM-Agent가 환경을 탐사하고 LM-Labeler가 결과를 바탕으로 지시를 재작성하므로, 기존 정답 데이터에만 의존하지 않고 탐사 과정에서 데이터를 만들며 자기 교정을 수행한다.

### 96. ④
[D-14. Planning의 두 종류]
Local Planning은 한 단계씩 step-by-step으로 계획해 단순하고 직관적이지만 장기 의존 문제가 발생할 수 있다. Global Planning은 실행 가능한 전체 계획 경로를 한 번에 생성하고 여러 툴을 Chain으로 조합해 복잡한 환경에서 안정적이다.

### 97. ②
[D-15. Local Planning / ReAct]
ReAct는 Reasoning과 Action을 결합한 방식으로 Thought, Action, Observation을 반복하며 환경과 상호작용한다. Local 계획에 적합하다. ①은 Plan-and-Solve, ③은 Reflexion, ④는 CoAct에 대한 설명이다.

### 98. ③
[D-16. Global Planning / Plan-and-Solve Prompting]
Plan-and-Solve는 전체 계획을 먼저 세운 뒤 그 계획에 따라 순차적으로 문제를 해결한다. 단순 step-by-step보다 체계적이고 안정적이어서 누락과 잘못된 순서, 중간 오류를 줄이는 효과를 목표로 한다.

### 99. ①
[D-17, D-18. Reflexion과 CoAct]
Reflexion은 수행한 Trajectory를 평가하고 잘못된 부분을 Reflection 단계에서 분석해 스스로 반성한 뒤 재시도한다. CoAct는 두 에이전트가 협력해 실행 도중 계획과 코드를 다시 검토하고 수정하여 Long-horizon Task의 성공률을 높인다.

### 100. ④
