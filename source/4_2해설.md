# 4-2 해설

### 1. ③
[A-2. AI 시스템에서 중요한 두 요소]
강의는 우수한 AI 모델링과 우수한 AI 시스템 아키텍처 두 가지를 강조한다. 좋은 모델 자체뿐 아니라 모델을 실제 시스템 안에서 어떻게 연결하고 동작시키는가가 중요하다는 의미다.

### 2. ②
[A-4. Transformer의 등장]
Transformer는 긴 문장 학습 능력을 높이고 병렬 학습을 가능하게 해 대규모 사전학습에 유리하며, 긴 문장에서 중요한 부분에 선택적으로 집중한다. ③은 C챕터 RAG, ④는 인간 피드백 기반 정렬에 해당한다.

### 3. ①
[A-5. Large Language Model]
MLM은 입력 일부를 가린 뒤 문맥을 이용해 가려진 토큰을 예측하고, NTP는 이전 토큰을 기반으로 다음 토큰을 예측한다. ②는 두 방식을 뒤바꾼 설명이다.

### 4. ④
[A-6. Multimodal Large Language Model]
MLLM은 텍스트와 이미지, 음성 등 여러 Modal 데이터를 결합해 작업을 수행하는 모델이다. 여러 자연어를 처리한다는 뜻이 아니므로 ①과 혼동하면 안 된다.

### 5. ②
[A-7. 범용 LLM과 의료 특화 LLM]
범용 LLM은 여러 도메인에서 폭넓게 대응하지만 전문 영역에서 깊이가 부족할 수 있고, 의료 특화 LLM은 진단과 처방 등 전문 지식에 더 깊게 접근한다. ①은 두 특성을 뒤바꾼 설명이다.

### 6. ①
[A-8. 의료진 Agentic AI]
Agentic Clinician AI는 환자 상황과 병원 환경, 의료진의 경험과 언어 습관, 실제 workflow까지 고려해야 한다. 단순 지식 제공을 넘어 의료진처럼 판단 흐름과 의사결정을 수행할 수 있어야 한다.

### 7. ③
[A-10. AI 발전의 흐름]
흐름은 Perception AI, Generative AI, Agentic AI, Physical AI 순이다. 지각에서 생성으로, 다시 자율 수행과 물리적 실체로 확장되는 순서를 기억해야 한다.

### 8. ②
[A-10. Perception AI]
Perception AI는 특정 분야를 예측하고 분석하는 전통 기계학습 기반 단계로 분류와 탐지, 인식, 예측이 예시다. ①은 Generative AI, ③은 Agentic AI, ④는 Physical AI의 설명이다.

### 9. ④
[A-10. Agentic AI]
Agentic AI는 능동적으로 작업을 수행하고 목표를 스스로 해결하기 위해 행동하는 단계이며, 강의는 이를 자율형 문제 해결 시스템으로 표현한다.

### 10. ①
[A-10. Physical AI]
Physical AI는 AI 시스템이 실제 물리적 실체를 갖고 현실 세계에서 작동하는 단계로 로봇과 자율주행 시스템, 수술 로봇이 예시다. ②는 Perception AI의 예시다.

### 11. ②
[A-14. 세탁기 예시로 보는 Agent]
AI Agent가 적용된 세탁기는 센서로 상태를 인식하고 세탁물 상태에 따라 세탁 방식을 결정하며, 도중에 변한 상태를 다시 확인해 필요하면 전략을 바꾼다. ①과 ③, ④는 일반 세탁기의 동작이다.

### 12. ③
[A-15. AI Agent 정의]
AI Agent는 AI를 사용하여 사용자를 대신해 목표를 추구하고 작업을 수행하는 소프트웨어 시스템이다. ①은 언어모델, ②는 RAG, ④는 C챕터 MCP에 대한 설명이다.

### 13. ①
[A-16. AI와 AI Agent의 차이]
AI는 문제에 대한 출력이나 예측을 생성하는 데 초점이 있고, AI Agent는 목표 달성을 위해 상태 인지와 계획, 행동, 결과 확인, 재행동을 반복한다. 강의는 둘의 경계가 모호하다고도 설명하므로 ④는 옳지 않다.

### 14. ④
[A-17. AI Agent의 주요 특성]
제시된 특성은 자율성, 인지, 기억, 추론과 계획, 학습과 적응, 동작과 도구 사용 여섯 가지다. 파라미터 압축과 같은 경량화 능력은 포함되지 않는다.

### 15. ②
[A-18. AI Agent의 과제]
학습 연구 영역의 과제는 Multi-Agent 협업과 Memory 및 Context 관리, 작업 관리, 확장성과 성능이다. 보안과 개인정보, 자율성과 책임, 추론 비용, 윤리와 편향성은 실제 응용 영역의 과제로 구분된다.

### 16. ③
[B-2. 개별 LLM의 한계]
개별 LLM은 부정확하거나 조작된 정보를 만드는 환각, 스스로 추론을 점검하기 어려운 자기비판 부족, 모델 크기 증가에 따른 성능 향상이 둔화되는 Scaling Law 한계를 갖는다.

### 17. ①
[B-3. 왜 Multi-Agent System인가]
기능한 Agent들이 협업하면 지식 공유와 역할 분담이 가능해져 복잡한 문제 해결 능력이 향상된다. 인간 조직과 유사하게 서로 다른 역할과 공동 목표, 협업 구조를 적용한다.

### 18. ④
[B-4. Multi-Agent의 핵심 효과]
여러 Agent가 서로 다른 관점에서 문제를 풀면 개별 Agent의 한계를 극복하고 자기성찰과 교차 검증을 통해 오류를 줄여 더 나은 최종 결과를 얻을 수 있다.

### 19. ②
[B-5. 다중 Agent 질의응답 예시]
Support Agent는 주장을 지지하고 Oppose Agent는 반론을 펴며 Research Agent가 근거를 수집한다. 최종 응답은 이들의 상호작용을 거쳐 만들어진다.

### 20. ①
[B-6. Multi-Agent System 구성 요소]
구성 요소는 Agent와 Environment, Interaction, Organization이다. ②는 C챕터 AI Agent 내부 구성, ③은 MCP 아키텍처, ④는 ReAct 루프에 해당한다.

### 21. ③
[B-7. Multi-Agent 협업 유형]
협업 유형은 Cooperation과 Competition, 그리고 둘을 결합한 Coopetition 세 가지다. ①은 통신 구조, ②는 협업 프로토콜의 분류이므로 혼동하면 안 된다.

### 22. ④
[B-8. Cooperation의 장점]
Cooperation은 전문화를 통해 계산 비용과 복잡성을 줄이고 오류를 감소시켜 신뢰성을 높인다. ①은 Competition의 장점에 해당한다.

### 23. ②
[B-9. Multi-Agent 협업 의사결정 과정]
전형적 구조는 Goal 정의, Expert Recruitment, Collaborative Decision-Making, Action Execution, Evaluation이며 새로운 상태를 반영해 여러 Round를 반복한다.

### 24. ①
[B-10. Cooperation 예시: 의료 협업]
역할은 난이도 판단 Agent, 전문가 모집 Agent, 초기 진단 Agent, 토론 Agent, 최종 판단 Agent로 분리된다. ③은 MetaGPT의 소프트웨어 개발 절차다.

### 25. ③
[B-11. Competition]
Competition은 더 강한 논리를 도출하고 숨겨진 오류를 발견하며 다양한 관점을 탐색하게 하지만, 끝나지 않는 토론과 계산 비용 증가라는 단점이 있다.

### 26. ②
[B-12. Cooperation과 Competition의 결합]
협력과 경쟁을 전략적으로 조합해, 같은 목표 달성을 위해서는 협력하고 일부 문제에서는 서로 경쟁하는 구조를 만들 수 있다. 인간 조직의 실제 의사결정 방식과 유사하다.

### 27. ①
[B-13. Mixture-of-Experts와 유사한 관점]
MoE는 다양한 전문가 모델 중 적절한 전문가를 선택해 활용한다. Multi-Agent 역시 역할 특화와 전문가 분리를 통해 유사한 장점을 얻을 수 있다.

### 28. ④
[B-14. 규칙 기반 프로토콜]
사전에 정의된 규칙으로 Agent 상호작용 방식을 미리 정하므로 통제하기 쉽고 인간의 협력 방식을 모방할 수 있지만, 모든 상황에 규칙을 적용하기 어려워 유연성이 부족하다.

### 29. ②
[B-15. 역할 기반 프로토콜]
사전에 각 Agent의 역할을 정의하고 역할에 따라 업무를 분담한다. Product Manager와 Architect, Project Manager, Engineer, QA Engineer가 예시다.

### 30. ①
[B-16. MetaGPT 스타일 협업]
흐름은 Requirement Analysis, Architectural Design, System Design, Coding, Testing, Acceptance Check 순이며 각 단계마다 역할 Agent가 배치되어 SOP 기반으로 협력한다.

### 31. ③
[B-18, B-19. 중앙집중형과 탈중앙화 구조]
중앙집중형은 중앙 Agent가 역할을 관리하고 조정하므로 전체 흐름 관리와 통제가 쉽지만 병목이나 실패지점이 될 수 있다. 탈중앙화는 일부 Agent 실패에 강하고 확장성이 높지만 Coordination이 어렵다.

### 32. ④
[B-20. Multi-Agent System의 주요 고려사항]
고려사항은 Agent 수 증가에 따른 확장성, 상황에 맞는 협업 전략 선택, 환경과 목표 변화에 맞춘 구성 및 역할 변경이라는 적응 가능성이다.

### 33. ②
[C-1. 패러다임 전환]
전통적 LLM은 고정된 파라미터와 메모리에 의존하며 대부분 입력에서 출력으로 이어진다. Agentic AI는 실시간 정보에 접근하고 외부 Tool을 활용하며 환경과 상호작용해 필요한 행동을 수행한다.

### 34. ①
[C-5. LLM 내부 메모리 한계]
한계는 학습 당시 지식이 고정되어 최신 정보를 반영하기 어려운 낡은 지식, 부정확한 정보를 만드는 환각, 기업 내부나 개인 정보에 접근할 수 없다는 점이다.

### 35. ③
[C-6. RAG의 핵심 아이디어]
RAG는 답변 생성 전에 외부 Source에서 관련 정보를 검색하고 그 결과를 바탕으로 답변을 생성한다. 최신성과 신뢰성, 검증 가능성, 근거 기반 응답이 장점이다.

### 36. ④
[C-7. 기본 RAG 파이프라인]
순서는 문서를 Chunking하고 Embedding Model로 벡터화해 Vector Database에 저장한 뒤, Retrieval과 Context Augmentation을 거쳐 LLM이 응답을 만드는 흐름이다.

### 37. ②
[C-8. 일반 RAG의 한계]
일반 RAG는 외부 지식 Source 하나만 사용하는 단순 구조에 한 번 검색하고 끝나는 일회성 방식이라, 여러 단계 추론이 필요한 복합 질의에 약하고 대화 맥락 유지도 어렵다.

### 38. ①
[C-9. Agentic RAG]
Agentic RAG는 AI Agent가 RAG 파이프라인을 능동적으로 조작해 검색 Source 선택과 Query 재작성, 검색 반복, 결과 평가, 재검색을 수행하는 구조다.

### 39. ③
[C-10. Agentic RAG가 할 수 있는 일]
검색 여부 결정과 Tool 선택, Query 생성, 결과 평가, 재검색, 여러 Source 비교를 수행한다. 즉 단순 Retrieval이 아니라 Search Strategy 자체를 Agent가 결정한다.

### 40. ②
[C-11. AI Agent 구성 요소]
구성 요소는 LLM과 Memory, Planning, Tools 네 가지다. ①은 RAG 시스템 요소, ③은 MCP 아키텍처, ④는 ReAct 루프에 해당한다.

### 41. ④
[C-12. Single-Agent RAG Router]
하나의 Retrieval Agent가 Query를 보고 여러 Tool 중 적절한 것을 선택하는 Router 역할을 수행한다. 여러 Agent가 소스를 나누는 것은 Multi-Agent RAG다.

### 42. ①
[C-13. Multi-Agent RAG System]
여러 Retrieval Agent가 각자 전문 Source와 Tool을 담당하므로 전문화와 병렬화, Source별 역할 분리가 가능하다.

### 43. ③
[C-15. 행동 정책의 세 요소]
Agent는 언제 Tool을 호출할지, 무엇을 사용할지, 어떻게 호출할지를 학습해야 한다. 호출 시점에는 반응 시간과 정확성 사이의 Trade-off가 존재한다.

### 44. ②
[C-17, C-18. Toolformer]
Toolformer는 소규모 API 호출 후보를 생성해 실행한 뒤, 그 호출이 문장 예측에 실제 도움이 되었는지 평가해 유용한 호출만 학습 데이터로 사용한다. 모든 Tool Call을 학습하지 않는 것이 핵심이다.

### 45. ④
[C-19. Gorilla]
Gorilla는 LLM을 대규모 API에 연결해 다양한 API를 정확히 호출하도록 하며 Hallucinated API Call을 줄이는 것을 목표로 한다. APIBench와 Retrieval을 활용한다.

### 46. ①
[C-20. ReTool]
ReTool은 전략적인 Tool 사용을 위한 강화학습으로, Tool 사용 여부와 시점 자체를 학습해 도구를 너무 많이 쓰거나 잘못 쓰는 문제를 개선한다.

### 47. ③
[C-21. Search-R1]
Search-R1은 LLM Agent가 자율적으로 다단계 검색을 수행하도록 강화학습으로 훈련해 답변 정확성과 판단력을 높인다. 알고리즘으로 GRPO를 사용한다.

### 48. ②
[C-22. GRPO]
GRPO는 개별 Value Model을 직접 쓰는 대신 같은 입력에서 여러 출력 결과를 비교해 상대적 보상을 계산한다. Group Relative Advantage가 핵심 개념이다.

### 49. ①
[C-23. Model Context Protocol]
MCP는 모델이 외부 Tool과 Resource, Environment와 원활히 상호작용하도록 하는 표준 인터페이스이며, 강의는 이를 AI 기능의 USB-C에 비유한다.

### 50. ③
[C-24. MCP가 중요한 이유]
M개의 Model과 N개의 Tool을 직접 연결하면 M×N개의 연결이 필요하지만, 표준화된 중간 Interface를 쓰면 M+N 수준으로 단순화된다.

### 51. ④
[C-25, C-26. MCP 구조와 기능]
MCP Host는 사용자가 사용하는 AI Application이고 Client는 Host 안에서 Server에 연결하며, Server는 표준 형식으로 Tool과 Resource, Prompt를 제공한다.

### 52. ②
[C-28. Agent2Agent Protocol]
MCP는 Agent와 Tool을 연결하고 A2A는 Agent와 Agent의 협업을 담당한다. A2A는 내부 Memory와 사고, 도구를 직접 공유하지 않고도 협업하도록 만든 프로토콜이다.

### 53. ①
[D-2. 단계적 사고의 중요성]
복잡한 문제를 풀기 위해 LLM은 단계별 사고 과정을 수행해야 하며, 중간 추론 과정을 거치면 정확도가 향상될 수 있다는 것이 핵심이다.

### 54. ③
[D-3. Chain-of-Thought Prompting]
Few-shot Prompting으로 Question과 Reasoning Example, Answer를 함께 제시하면 모델이 유사한 문제에서도 단계적 추론을 수행한다. 산술과 논리, 다단계 추론에서 성능이 향상된다.

### 55. ②
[D-4. Zero-shot Chain-of-Thought]
Few-shot Example 없이도 단계적으로 생각하자는 문구를 통해 추론 과정을 유도할 수 있다. Zero-shot Prompting으로 Chain-of-Thought를 활성화하는 방식이다.

### 56. ④
[D-5. Self-Consistency]
여러 Reasoning Path를 생성해 다양한 답 후보를 확보하고 다수결이나 통계적 방식으로 최종 답을 선택한다. 하나의 CoT만 쓰면 잘못된 경로를 택할 수 있다는 문제를 보완한다.

### 57. ①
[D-6, D-7. Tree of Thoughts]
ToT는 여러 Thought를 생성하고 Value Prompt로 평가한 뒤 좋은 경로만 확장하며 BFS나 DFS로 탐색한다. 즉 Reasoning을 Tree Search 문제로 확장한 것이다.

### 58. ③
[D-9. ReAct]
ReAct는 Reasoning과 Acting을 결합해 Thought, Action, Observation을 반복하고 최종 답에 도달한다. 외부 정보를 활용하고 중간 결과를 반영하므로 실제 환경 Task에 적합하다.

### 59. ②
[D-10. HuggingGPT]
HuggingGPT는 Task Planning과 Model Selection, Task Execution, Response Generation 순으로 진행되며 LLM이 Planner와 Model Selector, Coordinator 역할을 수행한다.

### 60. ④
[D-11. Plan-and-Act]
Planner가 전체 계획을 세우고 Executor가 계획에 맞춰 행동한 뒤 Observation을 수집하며, 필요하면 Replan하고 다시 실행한다. 장기 Task와 다단계 수행에 적합하다.

### 61. ①
[D-12. Test-Time Compute]
추론 시 Computation을 더 많이 투자할수록 LLM 성능이 향상될 수 있으며, 낮은 난이도 Task에서는 모델 크기를 키우는 것보다 효율적일 수도 있다.

### 62. ③
[D-13. Test-Time Scaling Law]
추론 시 더 많은 Sample과 더 긴 Reasoning, 더 많은 Search와 여러 Revision을 수행하면 Accuracy가 증가할 수 있다. Inference Compute 자체가 성능 향상 요인이다.

### 63. ②
[D-15. 추론 모델 강화]
모델이 정확한 답뿐 아니라 올바른 Reasoning Format과 Process를 학습하도록 Reward를 설계할 수 있으며, 추론 과정과 최종 답을 태그로 분리해 학습한다.

### 64. ④
[D-17. 과도한 추론 문제]
긴 CoT는 성능을 높일 수 있지만 무조건 길면 비용이 증가하는 Overthinking 문제가 생긴다. 쉬운 문제는 짧게, 어려운 문제는 길게 필요한 만큼만 생각해야 한다.

### 65. ①
[D-19. 모델 기반 접근: DeGRPO]
첫 번째 생성 토큰에 짧은 추론과 긴 추론을 지시하는 Mode 선택 신호를 사용해, 모델이 문제 난이도에 따라 Short Reasoning과 Long Reasoning을 선택하도록 제어한다.

### 66. ③
[D-20. 추론 결과 기반 접근: InfiniThink]
여러 추론 과정을 Chunk처럼 나누어 처리하고 중간 Thought를 Summary로 압축해 다음 Iteration에 활용한다. Context Length 관리와 장기 Reasoning 유지가 장점이다.

### 67. ②
[D-21. 입력 Prompt 기반 접근: Routing]
Query의 난이도에 따라 빠른 모델과 강한 모델, 짧은 Reasoning과 긴 Reasoning으로 보내는 방식이다. 쉬운 질문은 연산을 적게, 어려운 질문은 더 많은 추론을 배정한다.

### 68. ④
[E-1. Deep Research의 배경]
패러다임은 Web Search, LLM Chatbot, RAG, Agent-Based Deep Research 순으로 변화했다. 단순 검색에서 답변 생성과 근거 결합을 거쳐 자율적 탐색과 분석으로 발전한다.

### 69. ②
[E-2. 왜 Deep Research Agent인가]
기존 LLM과 RAG는 한 번 검색하고 종료되며 검색 Source가 제한되어 다단계 정보 수집이 어렵고 계획과 수정 능력이 부족하다. Deep Research Agent는 검색을 반복하고 계획을 변경한다.

### 70. ①
[E-3. Agent 기반 심층 연구의 핵심]
LLM과 다단계 추론, 검색을 결합하고 검색 결과에 대한 동적 Feedback Loop를 사용하며, 단순 응답 생성이 아니라 능동적 정보 탐색과 Tool 및 다른 Agent와의 협업을 수행한다.

### 71. ③
[E-4. 검색과 추론 결합]
기존 RAG는 검색과 추론을 단순 연결하지만 복잡한 연구에는 부족하다. Agent가 필요한 정보를 인지하고 Query를 세분화해 추가 탐색을 수행해야 한다.

### 72. ④
[E-4. 효율적 Resource 할당]
탐색 경로가 길어지면 시간과 Token, API Cost가 증가하므로 병렬 탐색과 Tool 선택 최적화를 통해 비용을 줄여야 한다.

### 73. ①
[E-5. 강화학습 기반 훈련]
훈련 방식은 ReAct 같은 Prompt 기반, Toolformer 같은 지도학습, 그리고 모델이 독립적으로 최적 전략을 발견하도록 하는 강화학습으로 구분된다.

### 74. ②
[E-6. Test-Time Scaling]
추론 TTS는 CoT와 Self-Refinement, Self-Consistency처럼 사고 과정을 늘리고, 검색 TTS는 검색 단계와 탐색 범위, Query 반복을 늘린다. 더 많은 Search는 더 높은 Cost와 Trade-off 관계다.

### 75. ③
[E-7. Deep Research 문제 해결 과정]
핵심 Cycle은 생각과 도구 사용을 번갈아 반복한 뒤 답변에 도달하는 것이다. 생각으로 전략을 정하고 검색과 탐색으로 정보를 모으며 부족하면 추가 Query를 생성한다.

### 76. ①
[E-9. 정보 추출 효율]
Web page 전체를 그대로 전달하면 Token 낭비가 크다. 따라서 필요한 부분만 추출하고 유효 정보만 저장하며 중요한 부분을 요약하는 처리가 필요하다.

### 77. ②
[E-11. 보상 설계]
형식 오류에는 음의 보상을 주고 올바른 형식의 답변에는 점수를 부여할 수 있다. 사실성과 논리성, 질문 적합성 등 Research Process의 품질도 Reward 설계 대상이 된다.

### 78. ②
[E-12. 성능 분석]
In-domain 평가 데이터는 NQ와 TQ, HotpotQA, 2Wiki이고 Out-of-domain 평가 데이터는 Musique와 Bamboogle, PopQA다. 특히 Bamboogle에서 실제 환경 학습 효과가 크게 나타났다.

### 79. ①
[E-13, E-14, E-15. 창발적 행동]
End-to-End 강화학습으로 다단계 계획 능력이 생기고, 첫 검색 결과에만 의존하지 않는 교차 검증과 결과가 부족하면 Query를 수정하는 성찰적 재검색이 나타난다. 확실하지 않으면 추측하지 않는 정직한 회피도 중요한 품질이다.

### 80. ③
[E-16, E-17. Deep Research의 한계]
Deep Research Agent는 Prompt와 검색 결과, Memory, 중간 추론까지 많은 Token을 사용해 비용이 크고 Multi-Agent는 더 비싸다. 병렬 처리 구조는 복잡한 문제에 유리하지만 간단한 Task에는 과도할 수 있다.
